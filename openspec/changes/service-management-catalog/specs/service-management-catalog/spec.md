# Service Management Specification

## Purpose

The Service Management domain SHALL provide a clean-slate Service Management surface with governed service catalog data, server-generated ticket identifiers, strict ticket-to-catalog compatibility, and deterministic XLSX bulk workflows.

## Requirements

### Requirement: Service Management module naming is explicit and separated

The system SHALL expose the ticketing surface as **Service Management** and keep its navigation, routes, and state isolated from unrelated domains.

#### Scenario: Module naming and route separation

- GIVEN an authenticated operator opens the application
- WHEN they access the Service Management area
- THEN the displayed module label SHALL be **Service Management**.
- WHEN they access other modules (inventory catalog, CI administration, etc.)
- THEN Service Management UI state and controls SHALL remain isolated.

### Requirement: Ticket IDs are server-generated numeric primary keys

The system SHALL use a server-generated numeric primary key as the user-visible `ticket_id`; clients SHALL NOT supply `ticket_id` when creating tickets.

#### Scenario: Single-ticket create returns generated numeric ticket ID

- GIVEN a ticket create request without client-supplied `ticket_id`
- WHEN the request passes validation
- THEN the API SHALL persist the ticket and return a numeric `ticket_id` generated by the server.

#### Scenario: Client-supplied ticket_id is rejected

- GIVEN a ticket create request with `ticket_id` present
- WHEN validation runs
- THEN the request SHALL fail with a deterministic validation error and no ticket SHALL be persisted.

### Requirement: Service catalog entries are typed, unique by `service_id`, and immutable by scope

The service catalog SHALL require and persist each record with:
- a unique `service_id`,
- a required, non-empty `name`,
- a required `SLA`,
- a required `description`,
- an immutable exclusive `service_type` in `{incident, service_request}`,
- and a required `value_stream` selected from the active dictionary.

#### Scenario: Valid catalog create is accepted

- GIVEN a catalog payload with unique `service_id`, non-empty `name`, valid `SLA`, non-empty `description`, `service_type` in `{incident, service_request}`, and active dictionary `value_stream`
- WHEN it is submitted
- THEN the catalog service SHALL be persisted.

#### Scenario: Catalog update does not permit service_type mutation

- GIVEN an existing catalog record with `service_type=incident`
- WHEN an update attempts to change `service_type` to `service_request`
- THEN the request SHALL fail with a validation error.
- GIVEN an existing catalog record
- WHEN an update changes mutable fields only (`name`, `SLA`, `description`, `value_stream`)
- THEN the allowed updates SHALL be applied when all validation rules pass.

#### Scenario: Duplicate names are allowed across types only when service IDs remain unique

- GIVEN two catalog payloads with the same `name` but different `service_type`
- WHEN both provide unique `service_id`
- THEN both SHALL be accepted.
- GIVEN two catalog payloads with the same `service_id`
- WHEN submitted
- THEN persistence SHALL fail for the duplicate `service_id`.

### Requirement: Ticket and catalog compatibility SHALL be enforced in both UI and backend

The system SHALL ensure that ticket workflows only allow catalog services with matching `service_type` at both UI interaction time and backend validation time.

#### Scenario: Backend rejects incompatible service mapping

- GIVEN a ticket payload of type `incident`
- WHEN it references a catalog service of `service_request`
- THEN the backend SHALL reject the request and create zero ticket records.

#### Scenario: UI prevents incompatible selection

- GIVEN a user creates or edits a ticket in the UI
- WHEN they open service selection for an `incident` ticket
- THEN the UI SHALL only present `incident` catalog services and block incompatible picks before submit.

### Requirement: Exactly one active assignee is required per ticket

The system SHALL require exactly one active assignee per ticket on single and bulk creation.

#### Scenario: Invalid assignee cardinality is rejected

- GIVEN a ticket request with zero assignees or multiple assignees
- WHEN validation runs
- THEN the request SHALL fail with a validation error.

#### Scenario: Inactive users cannot be assigned

- GIVEN a ticket request selecting an inactive user
- WHEN validation runs
- THEN the request SHALL fail with a user-activity violation.

### Requirement: User deactivation is logical and preserves historical ticket context

The system SHALL preserve historical ticket assignment references when an active user is later deactivated, without retroactively mutating historical ticket rows.

#### Scenario: Historical ticket assignment remains readable

- GIVEN a ticket assigned to a user that is later deactivated
- WHEN an operator views past tickets and history
- THEN the historical assignee identity SHALL remain visible with its deactivated status.

### Requirement: XLSX catalog import is atomic, structured, and template-driven

The system SHALL support atomic catalog imports from a dedicated template with per-row validation and machine-readable feedback.

#### Scenario: Catalog template and validation contract

- GIVEN a user downloads the catalog import template
- WHEN the workbook is generated
- THEN it SHALL include required headers for `service_id`, `name`, `SLA`, `description`, `service_type`, and `value_stream`.
- GIVEN a catalog import workbook with one or more invalid rows
- WHEN processing runs
- THEN the API SHALL return row- and field-level validation errors and persist zero records.
- GIVEN a catalog import workbook with only valid rows
- WHEN processing runs
- THEN all records SHALL be persisted in one atomic commit.

### Requirement: XLSX ticket import is atomic, template-based, and compatibility-aware

The ticket bulk import workflow SHALL provide a template that includes both ticket rows and a reference worksheet, and SHALL be atomic with structured feedback.

#### Scenario: Ticket import template with reference data

- GIVEN a user downloads the ticket import template
- WHEN it is opened
- THEN it SHALL contain a ticket input sheet and a reference sheet listing valid catalog services filtered by `service_type` (including value-stream context).

#### Scenario: Ticket import validates assignee, compatibility, and fields

- GIVEN an uploaded ticket template containing invalid entries (missing assignee, invalid/inactive user, incompatible catalog service, or malformed required fields)
- WHEN processing starts
- THEN no tickets SHALL be created and the response SHALL include structured failures by row and field.

#### Scenario: Ticket import success path

- GIVEN an uploaded ticket template where every row is valid
- WHEN processing completes
- THEN all tickets SHALL be created atomically, each with one generated numeric `ticket_id` and one active assignee.

### Requirement: Strict TDD is mandatory for implementation evidence

The project SHALL follow strict TDD for this domain: tests that fail first, then implementation, then refactor.

#### Scenario: TDD evidence is produced before delivery

- GIVEN implementation work starts for this change
- WHEN verification is performed
- THEN each requirement in this spec SHALL have direct automated coverage, including negative and positive cases, with evidence of failing-first test sequencing.

## Risks

- Controlled dictionary values can introduce rollout friction if governance data for `value_stream` is incomplete.
- XLSX ingestion edge cases (formatting, hidden rows, large files) can increase validation complexity and require stronger QA before release.
