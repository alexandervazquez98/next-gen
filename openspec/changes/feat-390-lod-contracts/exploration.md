## Exploration: #390 finalize LOD graph overview and detail contracts

### Current State
- The existing CMDB graph route is `GET /api/graph/full`: `backend/main.py` mounts `routers.links` under `/api`, `backend/routers/links.py` accepts `layer`, `location`, and `owner`, and delegates to `link_service.get_full_graph()`. The service calls `topology_repo.get_filtered_graph_data()`, which currently materializes all matching CI nodes and links. The response shape is an untyped `{ "nodes": [...], "links": [...] }`; node mapping preserves existing fields such as `ip`, `public_ip`, `metrics`, and broad `metadata`, while links preserve `relationship` and optional tunnel `medium`. A non-admin with no allowed locations is short-circuited to an empty graph. The route has `CURRENT_USER_DEP` (active-user authentication), even though old test comments describe the links router as public; the runtime route, not those comments, is the compatibility baseline.
- `GraphCMDB` currently calls `useGraphTopologyQuery()` twice (filtered data and an unfiltered full graph) and both queries hit `/graph/full` with a 30-second poll. It computes location clusters, cluster counts, aggregate inter-cluster links, and search matches in memory after full hydration. Clicking a cluster only changes local rendering/selection; it does not request a detail subgraph. Search traverses the hydrated node object, including metadata. `NetworkVisualizer` independently polls `/api/graph/full` every 5 seconds; the App export and visual relationship/editor consumers also remain full-topology consumers.
- The canonical #230 spec already pins the behavioral direction: Location is the first overview axis; overview aggregates are post-authorization and omit raw sensitive node metadata; detail is demand-driven and selected-cluster-only; search/filter resolution uses only visible candidates and allowed public axes/labels; hidden and absent clusters are externally indistinguishable; overview and detail share authorization scope; zoom alone must not hydrate detail; `/graph/full` remains unchanged; and streaming, ML clustering, visual redesign, and implementation in #230 are out of scope.
- The archived #230 design contains a useful candidate wire shape but not executable contracts: overview fields are `axis`, `filters`, `generated_at`, `revision`, `aggregate_policy`, `clusters`, `inter_cluster_links`, `legend`, and `page`; detail fields are `cluster`, `filters`, `generated_at`, `revision`, `nodes`, `links`, `empty_reason`, and `page`. It proposes `location:<url-safe-key>`, `location:__unassigned__`, `minimum_count = 5`, and a default detail limit of `500`. These are design inputs for #390 to ratify, not code already present.
- No backend graph DTO/schema module, overview/detail route, graph cursor implementation, graph revision source, or graph-specific `cluster_id` parser exists. There is no `backend/schemas/` or `backend/security/` package in the current tree. The only frontend graph response type is `GraphTopologyResponse` with `{ nodes: GraphNode[]; links: GraphLink[] }`.
- Authorization is currently location filtering duplicated between the graph service/repository paths, not a reusable authorized field-projection helper. `get_full_graph()` copies non-internal raw node properties into `metadata` and exposes `public_ip`; no aggregate-breakdown permission exists in `UserPermission`. `allowed_ci_types` is stored on users but is not applied by the current graph path. Therefore #230's instruction to reuse the existing `/graph/full` projection policy cannot yet be confirmed as a concrete helper; #390 must document the dependency without changing `/graph/full`.

### Affected Areas
- `openspec/specs/cmdb-graph-level-of-detail/spec.md` — canonical behavioral constraints that the concrete DTO/runtime contract must satisfy.
- `openspec/changes/archive/2026-07-08-cmdb-graph-level-of-detail/design.md` — prior candidate field names, examples, pagination/cache ideas, trigger matrix, and security rules to ratify rather than redesign.
- `backend/routers/links.py` — eventual additive route signatures and validation boundary for `/graph/overview` and `/graph/detail/{cluster_id}`; `/graph/full` must remain untouched.
- `backend/services/link_service.py` — current graph scoping/mapping path and likely boundary for visibility, cluster-id, revision, and DTO conversion decisions.
- `backend/repositories/topology_repo.py` — current full-materialization Cypher path; future aggregate/detail queries and deterministic pagination must not blindly inherit its endpoint-OR behavior.
- `backend/models/core.py` (or a new graph DTO module) — current `Node`/`Link` models are mutation/domain models, not overview/detail response schemas.
- `backend/models/user.py` and `backend/services/auth_service.py` — current role, location scope, permission, and authentication semantics; no aggregate-breakdown permission or shared graph projection helper is defined.
- `backend/tests/test_routers_links.py` and `backend/tests/test_topology_repo_nodes.py` — `/graph/full` compatibility and scoping regression baseline; new schema/serialization contract tests belong beside them or in a dedicated graph-contract test module.
- `frontend/services/queryResources.ts`, `frontend/services/queryKeys.ts`, and `frontend/hooks/queries/useGraphTopologyQuery.ts` — current full-topology type, URL serialization, polling, and cache-key conventions to mirror without migrating consumers in #390.
- `frontend/types.ts`, `frontend/components/GraphCMDB.tsx`, and `frontend/components/NetworkVisualizer.tsx` — frontend DTO consumers and migration boundaries for #392/#393, not implementation scope for the contract slice.

### Gaps vs. Issue #390 acceptance bullets
- **1. Define DTO/schema contracts for `GET /graph/overview`.** — The high-level contents and Location-first behavior are pinned by #230, and the archived design proposes a shape, but no Pydantic response model, TypeScript interface, exact null/omission rules, filter encoding, or OpenAPI contract exists. #390 still needs to make the overview wire schema authoritative.
- **2. Define DTO/schema contracts for `GET /graph/detail/{cluster_id}`.** — The selected-subgraph contents, parent references, projection flags, and empty-result concept are pinned; the archived design supplies candidate fields. Exact node/link/boundary-stub shapes, error model, visible-cluster metadata rules, and serialization behavior remain to be finalized, with no implementation present.
- **3. Keep `GET /graph/full` unchanged.** — Already pinned and exercised by the current route/service/tests: preserve the `{nodes, links}` response and existing semantics, including current field projection behavior. #390 should add compatibility assertions/documentation only; it must not “clean up” or strengthen `/graph/full` redaction.
- **4. Define stable `cluster_id` semantics with axis derived from the identifier.** — Location-first and the `<axis>:<url-safe-key>` direction are pinned, including an `Unassigned` fallback in the prior design. Canonical key normalization, case sensitivity, Unicode/reserved-character handling, delimiter/path escaping, collision guarantees, malformed/unsupported-id errors, and the exact `__unassigned__` rule still need decisions.
- **5. Define pagination/cursor/limit rules for large clusters.** — The spec requires bounded detail before production and the prior design suggests opaque cursors and `limit=500`, but graph code has no cursor path (existing pagination elsewhere is offset-based). #390 still owes default/min/max limits, deterministic node/link ordering, cursor binding to cluster/filter/revision, invalid/expired/stale-cursor behavior, and whether overview cluster pages are paginated at all.
- **6. Define `revision` / cache invalidation semantics.** — An opaque revision that changes when the caller-visible topology changes is the established design direction, and the prior design describes React Query invalidation at a high level. There is no graph revision source or consistency rule; #390 must define visibility/filter scope, snapshot consistency between overview/detail, stale detail/cursor handling, and whether conditional requests/ETag behavior is part of the contract.
- **7. Define non-enumerating hidden/absent cluster behavior.** — The requirement that hidden and nonexistent clusters be indistinguishable is firmly pinned. The prior design suggests a `200` response with `cluster: null`, empty arrays, `empty_reason: "unavailable"`, and the normal page shape, but #390 must ratify that exact status/body/header/timing behavior and ensure no cluster metadata or pagination signal leaks existence. No code currently implements it.
- **8. Define visible-candidate-only search/filter target resolution.** — Post-authorization visibility and the one/multiple/zero/ambiguous outcomes are pinned by #230. The exact searchable fields, public axes/labels, filter precedence, query parameter shape, server-versus-client resolution ownership, and response representation are unresolved. Current `GraphCMDB` searches full hydrated nodes locally, while the backend search path is separate and only location-scoped; neither implements the LOD target contract.
- **9. Define aggregate disclosure rules and sensitive-field policy for future LOD endpoints.** — Overview omission of raw sensitive fields and suppression/bucketing of low-cardinality aggregates are pinned. The prior design proposes a minimum of five and `graph:aggregate_breakdown:read`, but that permission is absent from `UserPermission`, and no shared projection helper exists. #390 must define the exact suppressed representation, permission name, per-bucket rules, safe geo precision, and a detail projection-policy interface while explicitly leaving `/graph/full` unchanged; the current raw `metadata`/`public_ip` behavior is a major dependency for #391.

### Approaches
1. **Mirrored typed contracts (Pydantic + TypeScript)** — Add a small backend graph-contract DTO module, pure cluster-id/cursor/revision validation types, and mirrored frontend interfaces/request signatures with serialization fixtures and schema tests. Keep route data access, Neo4j aggregation, and component migration in #391/#392/#393. This matches the existing stack, avoids introducing a code-generation pipeline, and keeps the contract reviewable.

2. **Backend-owned OpenAPI with generated frontend types** — Make FastAPI/Pydantic the sole source of truth and introduce an OpenAPI-to-TypeScript generation step for the frontend. This can reduce long-term drift, but no OpenAPI code-generation tooling or workflow was found in the repository; adding and maintaining that toolchain would expand #390’s footprint and couple the contract slice to CI/build configuration.

### Recommendation
Treat #390 as an additive, schema-first contract slice ahead of #391: ratify the archived design’s field names and examples, then materialize backend Pydantic DTOs plus mirrored TypeScript types and strict serialization/validation fixtures for authorized, redacted, empty, paginated, and hidden/absent cases. Define a canonical location cluster-id codec, context-bound opaque cursor rules, visibility-scoped revision semantics, exact `200/unavailable` behavior, visible-only search resolution vocabulary, aggregate suppression/permission policy, and a named detail projection-policy interface, while making no Neo4j query, endpoint behavior, GraphCMDB migration, or `/graph/full` change. Plan two work-units: backend contract/value-object models and tests, followed by frontend type/request/cache-contract mirrors and cross-layer fixtures; #391 then implements the additive APIs, #392 migrates GraphCMDB, and #393 handles remaining consumers.

### Risks
- No existing graph field-projection helper exists: the current full-graph service forwards broad raw metadata and `public_ip`, so a new detail policy can drift or accidentally become a breaking `/graph/full` redaction change.
- `UserPermission` has no aggregate-breakdown permission, and the codebase has no tenant identifier; current graph scoping is primarily `allowed_locations` (with `allowed_ci_types` ignored), so “authorization parity” needs an explicit interpretation.
- `get_filtered_graph_data()` applies an endpoint-OR location condition to links while separately materializing scoped nodes; reusing it for LOD can expose out-of-scope endpoint identifiers or create unsafe boundary aggregates/stubs.
- There is no topology revision counter/change feed. A timestamp/hash implementation must be visibility-scoped and must not reveal hidden topology changes through cache behavior.
- Cluster keys may contain colons, slashes, Unicode, empty values, or case variants; an ambiguous codec can cause collisions or path-routing/security bugs.
- Exact counts, edge weights, geo summaries, and “has more” signals can become low-cardinality or hidden-cluster oracles unless suppression is applied after authorization and consistently across every response field.
- Existing full-graph consumers poll at different cadences and `GraphCMDB` currently performs a second unfiltered query for location options; migration coupling belongs to later issues but can distort the contract if not kept out of #390.
- Strict TDD requires real schema/serialization assertions in this slice; relying only on documentation examples would leave drift undetected before #391.

### Ready for Proposal
Yes — #390 is ready for proposal as a bounded, additive contract-finalization slice. The orchestrator should tell the user that #230 already fixes the behavioral invariants, while #390 must ratify the exact wire/runtime decisions above without implementing backend queries or frontend migration; #391 owns API rollout, #392 owns GraphCMDB orchestration, and #393 owns remaining consumers. The proposal should explicitly preserve `/graph/full` and call out the missing projection helper, aggregate permission, and tenant/scope interpretation as contract prerequisites.

### Estimated file footprint
Approximately **250–350 changed LOC across 6–8 files** for the apply phase: one new backend graph DTO/validation module, one backend contract-test module, small frontend type/request/cache additions, and one frontend serialization/query-contract test module. This should remain below the 400-line review budget if route/query implementation and consumer migration stay in #391–#393; including those would push the work beyond the intended contract slice.
